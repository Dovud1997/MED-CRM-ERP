# Обзор продукта и требования (PDR)

**Проект**: ONA VA BOLA KLINIKASI (`clinicos`)
**Тип**: API-first CRM/ERP для частной клиники
**Обновлено**: 2026-08-21
**Статус**: активная разработка (Foundation + операционные модули)

## Что это

`clinicos` (бренд — ONA VA BOLA KLINIKASI) — система управления частной клиникой,
построенная как API-first платформа. Все бизнес-правила и данные живут в backend,
а любой клиент (веб-панель, будущие мобильное и Telegram-приложения, ТВ-экраны очереди)
обращается к единому версионированному REST API `/api/v1`.

Источник истины — PostgreSQL. Backend написан на Go. Веб-панель — Next.js.
Мобильное приложение — Flutter. Проект русскоязычный, интерфейс локализован на
русский, узбекский и английский языки.

## Зачем

Заменить разрозненные таблицы и бумажный учёт единой системой, которая:

- ведёт единую карточку пациента и неизменяемую клиническую хронологию;
- управляет сотрудниками, филиалами, специальностями и настраиваемыми ролями;
- планирует приёмы с защитой от пересечений на уровне базы данных;
- обслуживает живую электронную очередь с публичными ТВ-экранами;
- закрывает операционный контур: касса, бухгалтерия, склад, стационар, отчёты;
- защищает персональные и медицинские данные (шифрование полей, аудит,
  зашифрованные резервные копии).

## Для кого

| Роль | Что делает в системе |
|------|----------------------|
| Владелец (`OWNER`) | Полный доступ, управление организацией, филиалами, ролями, резервные копии, архив чатов |
| Врачи (`DOCTOR_*`, `SPEECH_THERAPIST`) | Приёмы, медкарта, диагнозы, назначения, лаборатория |
| Рецепшн (`RECEPTIONIST`) | Пациенты, запись, расписание |
| Кассир (`CASHIER`) | Касса, оплаты, долги пациентов |
| Бухгалтер (`ACCOUNTANT`) | Бухгалтерия, обязательства, зарплаты, финансовые отчёты |
| Менеджер (`MANAGER`) | Чтение оперативных данных (филиалы, сотрудники, пациенты, записи) |

Роли — permission-based, deny-by-default. Каждый эндпоинт защищён конкретным
permission (`patients:read`, `clinical:write`, `finance:write`, `queue:call` и т. д.).
Владелец получает wildcard-доступ (`*`).

## Реализованные возможности

Функциональность подтверждена по коду (`apps/api/internal/app`, миграции
`apps/api/migrations`, роуты в `apps/api/internal/app/http.go`) и по журналу задач
(`TASKS.md`).

### Идентификация и доступ
- Логин по паре организация + логин + пароль, пароли — Argon2id.
- JWT access-токен и ротируемый refresh-токен; refresh хранится только как SHA-256 hash.
- Permission-based RBAC, изоляция по организации (tenant scope) в каждом запросе.
- Append-only журнал аудита (`audit_logs`) без клинического содержимого.

### Организация и персонал
- Филиалы (транзакционное создание, guard, tenant isolation, аудит).
- Сотрудники: привязка к филиалу, должности, специальности и нескольким ролям.
  Паспорт, адрес, приватный телефон шифруются (`pgcrypto`); публичные email/Telegram
  отделены от приватного профиля.
- CRUD пользовательских ролей + системные роли клиники (см. `cmd/seed`).
- Справочник специальностей и диагнозов (МКБ-10) по специальностям.

### Пациенты и клиника
- Реестр пациентов, поиск по ФИО, дедупликация по необратимому хешу телефона,
  шифрование чувствительных полей.
- Медицинская карта: группа крови, аллергии, прививки, рост/вес.
- Структурированные анализы: общий анализ крови (14 показателей, нормы м/ж),
  анализ мочи (17 показателей); обязательные защищённые вложения-фото.
- Диагностика: МРТ, КТ, рентген с обязательным файлом и защищённым просмотром.
- Диагнозы и назначения (МКБ-10, статусы, врач, филиал, неизменяемая история).
- Лабораторный workflow: тесты, направления, статусы, результаты.
- Неизменяемая хронология визитов (новый визит не перезаписывает предыдущий).

### Запись и расписание
- График врачей: недельные смены, выходные, перерывы.
- Создание записи с выбором пациента/филиала/врача, длительностью, причиной.
- Статусы приёма: запланирован, подтверждён, прибыл, идёт приём, завершён,
  отменён, не пришёл.
- Пересечение записей одного врача и запись вне смены запрещены на уровне PostgreSQL.
- Дашборд: показатели за сегодня и ближайшие будущие записи.

### Электронная очередь и ТВ
- Номера очереди, действия `CALL`/`RECALL`/`START`/`COMPLETE`/`SKIP`/`CANCEL`.
- Кабинеты и ТВ-экраны с криптографическими токенами (в БД — SHA-256 hash).
- Публичный TV Display (`/display/{token}`) с SSE, переподключением, часами,
  последними вызовами, бегущей строкой, режимом конфиденциальности `NUMBER_ONLY`.
- Медиатека (аудио/видео/баннеры/логотипы/QR) в отдельном Docker volume `queue_media`,
  с возможностью переезда на S3/MinIO без смены API.
- Подробности: `docs/deployment/ELECTRONIC-QUEUE.md`.

### Операционный и финансовый контур
- Услуги и цены: категории, цены по филиалам, индивидуальные цены врачей.
- Стационар: палаты, койки, цена за сутки, бронирование/заселение/выписка,
  запрет пересечения брони одной койки (exclusion constraint).
- Касса: смены, оплаты (наличные/карта/перевод/в долг), возвраты, расходы,
  лицевой счёт пациента, долги на сегодня, сверка при закрытии.
- Бухгалтерия: доходы/расходы, обязательства, начисления и выплаты сотрудникам,
  дебиторская задолженность, отчёт CSV.
- Склад: партии, сроки годности, ответственные, закрепление оборудования,
  инвентаризация, адресное размещение.
- Отчёты: период и филиал, динамика по дням, загрузка врачей, сравнение филиалов, CSV.
- Внутренний чат сотрудников с непрочитанными, аудитом и owner-only архивом.
- Конструктор печатных документов (назначения, рецепты, чеки; A4/A5/80 мм).

### Данные и резервные копии
- Пользовательский экспорт `.ovbk`: AES-256-GCM, ключ из Argon2id, пароль не хранится.
- Утилита проверки целостности `backupcheck`.
- Подробности: `docs/deployment/BACKUP-RESTORE.md`.

## Нефункциональные требования

- Stateless API, горизонтально масштабируемый; состояние — в PostgreSQL/Redis.
- Health/readiness эндпоинты (`/api/v1/health/live`, `/api/v1/health/ready`).
- Structured logs без PII, correlation id (`X-Request-ID`).
- Security-заголовки, строгий CORS allowlist, параметризованные SQL-запросы (`pgx`).
- Web-аутентификация через HttpOnly, `SameSite=Strict` cookies (BFF в Next.js).
- Подробнее по безопасности — `SECURITY.md` в корне репозитория.

## Ограничения и не реализовано

- Мобильное приложение (Flutter) на этапе scaffold; входа пациента (`PATIENT`) в
  backend пока нет — см. `MOBILE_INTEGRATION_PLAN.md`. По решению владельца
  (2026-08-09) backend/web не меняются под mobile.
- Нет WebSocket; realtime сейчас через HTTP polling (web) и SSE (ТВ-очередь).
- Онлайн-платежи Узбекистана (Click/Payme) не подключены — только офлайн-касса.
- Файловый S3-модуль с антивирусным сканированием и retention — в планах (этап 3).
- Worker/outbox и провайдеры уведомлений (SMS/email/Telegram) — в планах.
- Юридическая часть (DPIA, согласия, сроки хранения под юрисдикцию Узбекистана)
  не сертифицирована. До обработки реальных медданных обязателен production gate
  (см. `docs/project-roadmap.md`).

## Открытые вопросы

1. Часть настроек TTL токенов (`ACCESS_TOKEN_TTL`, `REFRESH_TOKEN_TTL_DAYS`) задана в
   `.env`, но `apps/api/internal/app/config.go` использует захардкоженные значения
   (15 мин / 30 дней) — переменные окружения фактически не читаются.
2. Точный перечень production-ролей и их permissions зависит от seed-данных
   (`cmd/seed`) и может отличаться от упоминаний в старых доках (`SECURITY.md`).
