# ONA VA BOLA KLINIKASI — безопасность медицинских данных

## Модель угроз

Защищаем персональные и медицинские данные от внешнего злоумышленника, скомпрометированной учётной записи, избыточных прав сотрудника, утечек через логи/backup/файлы и ошибок tenant isolation. Отдельно учитываются ransomware, supply-chain compromise и потеря инфраструктуры.

## Контроли

- TLS 1.2+ снаружи; приватная сеть между сервисами; шифрование дисков/backup на инфраструктурном уровне.
- Argon2id для паролей. JWT access 15 минут, ротация refresh token, server-side revoke, generic login errors.
- Deny-by-default RBAC: `OWNER`, `ADMIN`, `DOCTOR`, `RECEPTIONIST`, `NURSE`, `ACCOUNTANT`.
- Tenant scope обязателен в каждом repository query. Идентификатор организации не принимается из body клиента.
- Audit события append-only: actor, action, entity, time, IP и correlation metadata без клинического содержимого.
- PII не пишется в application logs. Секреты поступают только через environment/secret manager.
- Паспортные данные, постоянный адрес и телефон сотрудников хранятся в PostgreSQL в зашифрованных полях `pgcrypto` и не возвращаются общим списком сотрудников. Публичные рабочие контакты (email и Telegram) отделены от приватного профиля.
- Телефон, паспорт, адрес и контакт опекуна пациента шифруются на уровне полей. Для предотвращения дублей используется необратимый хеш нормализованного телефона; общая выдача пациентов не содержит расшифрованных контактов.
- S3 buckets private; presigned URLs короткоживущие; upload проходит type/size validation и malware scan.
- Rate limiting, security headers, строгая CORS allowlist, input validation и параметризованные Prisma queries.

## Эксплуатация

- Раздельные production/staging environments и least-privilege service accounts.
- Ежедневные encrypted backups, immutable/off-site copy, регулярная проверка восстановления.
- Клиническая история ведётся как добавляемая хронология: новый визит не перезаписывает предыдущий. Изменения группы крови, аллергий и визитов фиксируются в audit log.
- Пользовательский экспорт `.ovbk` шифруется AES-256-GCM с ключом Argon2id и отдельным паролем, который сервер не сохраняет. Минимальный технический срок хранения медицинской карты — 3 года и может быть увеличен политикой организации.
- Зависимости сканируются в CI; критические CVE блокируют релиз.
- Доступ персонала пересматривается регулярно и отзывается при увольнении немедленно.
- Инциденты: containment, сохранение evidence, оценка затронутых субъектов, уведомление по требованиям применимой юрисдикции.

## Защита электронной очереди

- Административные операции разделены permissions `queue:read`, `queue:manage`, `queue:call`, `queue:settings`, `queue:media`, `queue:audio`, `queue:display`.
- Публичный экран получает минимальный набор данных. Режим по умолчанию `NUMBER_ONLY` не раскрывает ФИО пациента.
- Токен экрана генерируется криптографически, в PostgreSQL хранится только SHA-256 hash; открытый токен возвращается только при создании или ротации.
- Загружаемые файлы проверяются по сигнатуре MIME, получают случайное имя, лежат вне `public` frontend и выдаются только после проверки токена и tenant scope.
- Все изменения очереди, экранов и медиатеки должны сохраняться в audit log; вызовы дополнительно фиксируются в `queue_call_history`.

Технические меры не являются юридической сертификацией. До production необходимо определить юрисдикцию (включая требования Узбекистана к персональным данным и локализации), сроки хранения, основания обработки, формы согласия и процедуру реализации прав пациента.
